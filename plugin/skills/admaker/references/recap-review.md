# 해설형 리뷰

작품의 이야기를 소개하면서 **내레이터의 반응·유머·해석·평가**까지 콘텐츠로 넣는 형식입니다. 줄거리는 시간순 해설형(`recap-chrono.md`)처럼 원작 순서대로 풀고, 줄거리가 끝나면 **리뷰 파트**를 따로 둡니다. 가장 큰 특징은 **작품의 장르와 목적에 따라 톤을 바꾼다**는 점입니다. 특정 채널의 말투·유행어·별명·코너 이름·브랜딩을 흉내 내지 않고, 문장은 매번 새로 씁니다.

`recap-chrono.md`에서 그대로 쓰는 것: 일곱 단계(§2), 잇는 말, 인물 첫 등장 이름, 반전 앞 의심(§4). 본편 문서(`recap-highlight.md`)에서 그대로 쓰는 것: 사전 조사, 장면 나누기·알아보기, 배우 대사 강조, 로고 띠 자르기, 자막, 소리, 목소리 일관성, 윤문, 마무리 효과 패스(§8.2).

## 1. 네 가지 형식 비교

| | 궁금증 설계형 | 시간순 해설형 | 해설형 리뷰 (이 문서) | 쇼츠 |
|---|---|---|---|---|
| 묻는 것 | 어떤 장면을 골라 어떻게 재배치할까 | 사건을 어떤 순서로 알기 쉽게 설명할까 | 사건을 설명하며 재미·해석·평가를 어떻게 전할까 | 어디서 말하지 않을까 |
| 내레이션 | 정보를 나눠 공개 | 사건을 순서대로 설명 | 설명 + 반응 + 평가 | 필요한 곳에만 |
| 유머 | 거의 없음 | 가벼운 한마디 | 톤에 따라 과장·비유·풍자까지 | 짧은 재치 |
| 끝 | 다음 궁금증 | 결말 + 작품명 | 결말 → **리뷰 파트**(주제·완성도·추천 대상) | 장면의 재미 |

## 2. 톤 고르기 (`tone`)

작품을 보고 하나를 고릅니다. 같은 채널 안에서도 작품마다 톤이 다른 것이 이 형식의 핵심입니다. 사용자가 정하지 않았으면 장르로 추천하고 `ask_user_choice`로 확인합니다.

| `tone` | 언제 | 내레이션 성격 | 반응·재치(`wit`·`reaction`) 양 |
|---|---|---|---|
| `social` 스토리 + 사회적 해석 | 사회 문제를 다루는 스릴러·드라마 | 초반 사건 설명 → 중반 의미 해석 → 후반 사회적 메시지와 현실 연결 | 25% 아래 |
| `comedy` 인물 관찰 + 개그 해설 | 코미디·생활 드라마 | 인물의 행동에 계속 반응, 시청자 반응을 대신 말함, 별명을 다시 불러 개그 흐름으로 잇기(`callback`) | 20–60% |
| `mystery` 미스터리 추적 + 정보 통제 | 추리·미스터리 | 단서가 쌓일 때마다 질문을 다시 던지고, 아는 것과 새로 드러난 것을 구분("그런데·사실·알고 보니·그 시각·또 다른 가능성") | 20% 아래, 의문 줄 2개 이상 |
| `critical` 비판 리뷰 + 풍자 | 완성도가 아쉬운 작품을 재미로 볼 때 | 장면을 보여 주고 문제점을 짚고 과장된 비유로 웃음을 만듦. 시청자에게 직접 말 걸기 | 20–60% |
| `emotional` 감정 몰입 + 시대 맥락 | 시대극·휴먼 드라마·감동 실화 | 시대 배경을 먼저 세우고, 인물의 꿈과 관계, 과거와 현재를 이어 감정을 쌓음. 농담·비판 줄임 | 10% 아래 |
| `topic` 주제형 사례 모음 + 지식 | 작품 한 편이 아니라 한 주제(현상·장면 유형) | 개념 정의 → 사례 → 설명(추가 지식) → 새 사례 반복 → 유래·정리 | 40% 아래 |

## 3. 내레이션 여섯 갈래

| 갈래 | 역할 (`role`) | 하는 일 | 모양 (예시는 새로 지은 문장) |
|---|---|---|---|
| 사건 설명 | `situation`·`causal`·`transition` | 무슨 일이 일어났는지, 다음 사건으로 | "그렇게 모든 의심이 한 사람에게 쏠리게 됩니다." |
| 즉각 반응 | `reaction` | 시청자가 할 반응을 대신 한마디 | "아니 이걸 혼자 간다고요?" |
| 재해석 | `wit`·`character` | 행동을 과장·비유로 다시 읽기 | "대화 대신 메뉴판만 정독하는 철벽." |
| 궁금증 | `suspense`·`withhold`·`twist` | 질문, 정보 미루기, 추측 고치기 | "대체 누가 불을 켠 걸까요?" |
| 지식 | `knowledge` | 배경지식·개념·시대 맥락 | "그 시절에는 자기 나라 글을 쓰는 것만으로도 벌을 받았습니다." |
| 평가 | `review` | 주제·완성도·연기·추천 대상 | "무서운 장면보다 숫자만 세는 시청자 수가 더 오래 남습니다." |

규칙:

- **장면마다 갈래를 판단합니다.** 모든 장면에 유머나 반전을 넣으면 해설이 부자연스러워집니다. 한 갈래가 내레이션의 절반을 넘지 않게 합니다.
- 반응·재치는 **장면에 있는 사실 위에** 얹습니다. 장면에 없는 일을 지어내 웃기지 않습니다.
- `comedy`는 한 번 붙인 별명·말버릇을 두세 번 다시 써서 짧은 장면을 하나의 흐름으로 잇습니다(beat에 `callback: "별명"`).
- `critical`의 풍자는 **작품의 만듦새(설정·연출·특수효과·전개)**를 향합니다. 배우의 외모·실제 사람을 깎아내리지 않고, 욕설·혐오 표현을 쓰지 않습니다.
- `emotional`은 아픈 역사나 상처를 자극적으로 쓰지 않습니다. 사실은 사전 조사(본편 §0.5)로 확인한 것만 씁니다.
- 광고·멤버십 안내 같은 채널 운영 문구는 넣지 않습니다(사용자가 따로 요청한 경우만).

## 4. 구조

```
작품 소개(intro) → 사건(incident) → 주요 장면 전개(sequence·conflict, 작은 반전 twist) → 결말(ending)
→ 리뷰 파트(review 1–3 beat: 주제 → 장단점·연기 → 추천 대상) → 마무리(outro)
```

- 리뷰 파트는 **줄거리 뒤에 따로** 모읍니다. 전체 beat의 30% 이하. 들어갈 때 짧은 장 제목과 전환으로 줄거리와 나눕니다(마무리 효과 후보에 나옴).
- `critical`은 중간에도 평가가 들어가지만 그건 `reaction`·`wit`로 쓰고, 정리는 리뷰 파트에서 합니다.
- `topic`은 단계가 다릅니다: `hook` → `concept`(주제 정의, `knowledge`) → `case`(사례)·`explain`(왜 그런지)을 번갈아 → (선택) `review` → `outro`(유래·정리). 사례를 4개 넘게 연달아 나열하지 않습니다.
- 리뷰 문장은 결과물에 있는 장면과 사전 조사로 확인한 사실만 근거로 씁니다. 별점·순위처럼 사실처럼 보이는 숫자를 지어내지 않습니다.

## 5. 기획 데이터와 검사

`recap-highlight.md` §2.6과 같은 JSON에 `"mode": "review"`, `"tone"`을 적습니다.

```json
{
  "mode": "review",
  "tone": "social",
  "durationSec": 420,
  "events": [ { "id": "E1", "chrono": 1, "characters": ["수아"] } ],
  "beats": [
    { "stage": "intro", "event": "E1", "narration": { "role": "situation", "text": "새벽 세 시, 문 닫은 놀이공원에서 생방송을 켜는 수아." }, "src": { "from": 30.0, "to": 34.2 } },
    { "stage": "incident", "event": "E2", "narration": { "role": "suspense", "text": "그런데 꺼진 회전목마가 혼자 돌기 시작하는데, 대체 누가 켠 걸까요?" } },
    { "stage": "sequence", "event": "E3", "narration": { "role": "reaction", "text": "아니 이걸 혼자 간다고요?" } },
    { "stage": "ending", "event": "E6", "narration": { "role": "emotion", "text": "결국 수아는 카메라를 끕니다." } },
    { "stage": "review", "narration": { "role": "review", "text": "제목이 놀이와 공포를 동시에 가리킨다는 점이 끝까지 힘을 줍니다." } }
  ]
}
```

`node templates/recap-plan.mjs check plan.json`(앱 `check_recap_plan`)이 보는 것: tone 있음, 시간순 해설형 규칙(intro 시작·incident·원작 순서·내레이션 60% 이상·잇는 말 반복·반전 앞 의심·첫 등장 이름), 톤별 반응·재치 비율, 리뷰 파트가 결말 뒤에 30% 이하로 있는지, 마지막이 review·outro인지, 미스터리 톤 의문 줄 2개 이상과 나눠 공개, 감정 톤 배경·감정 줄, 개그 톤 callback, 한 갈래가 절반을 넘는지. `topic`은 concept 시작, 사례 3개 이상, 사례 4연속 금지, explain 있음, outro로 끝.

## 6. MCP 진행 순서

1. 본편 §8의 1–3번(확인, 사전 조사, 대사 뽑기, 장면 나누기, 알아보기, 로고 띠)을 그대로. 사전 조사에서 작품의 주제·시대 배경·평을 같이 모읍니다(리뷰 파트 근거).
2. 톤을 추천하고 고르게 함 → 원작 시간순 사건표 + beat 표(단계·갈래·문장·장면, 리뷰 파트 포함) → `check_recap_plan { plan: { mode: "review", tone, … } }` → 사용자 확인.
3. 윤문(본편 §3.1): 반응·재치 줄이 장면 사실 위에 있는지, 톤이 한 편 안에서 흔들리지 않는지, 리뷰가 줄거리와 겹치지 않는지.
4. 목소리: 톤에 맞는 스타일 태그 하나를 한 편 내내(`comedy`·`critical`은 가볍고 빠르게, `emotional`은 낮고 느리게) → `check_voice_consistency`.
5. `place_story_shots` → 자막 → BGM(리뷰 파트는 더 낮고 잔잔하게) → 마무리 효과 패스(본편 §8.2, `finishing`) → 검수.

## 7. 검수 체크리스트

- [ ] 톤이 작품의 장르·정서와 맞고 한 편 안에서 흔들리지 않는다.
- [ ] 반응·재치·풍자는 장면에 있는 사실 위에 있고, 모든 장면에 들어가지 않았다.
- [ ] 풍자는 작품의 만듦새를 향하고 사람을 깎아내리지 않는다. 욕설·혐오 표현이 없다.
- [ ] 줄거리가 끝난 뒤 리뷰 파트(주제·장단점·추천 대상)가 짧게 따로 있다.
- [ ] 리뷰의 근거는 결과물 장면과 확인한 사실뿐이고, 지어낸 숫자·평가가 없다.
- [ ] 특정 채널의 유행어·별명·코너 이름을 쓰지 않았다.
